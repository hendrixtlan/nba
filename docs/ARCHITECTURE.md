# Architecture

## 1. Scope

This repository implements a reference architecture for commercial Next Best Action decisioning with an agentic interface. The authoritative commercial recommendation is generated by governed ML and deterministic policy services, not by an LLM.

## 2. Logical layers

### Experience layer
Business applications, seller tools, BI experiences or copilots request a decision or an explanation.

### Agent layer
A Foundry-hosted or enterprise-approved agent interprets user intent and calls allow-listed tools. The agent can retrieve context, request the NBA decision, explain evidence and submit approved downstream actions. It cannot directly rewrite scores, bypass constraints or fabricate decision facts.

### Decision layer
The NBA service generates candidates, calls the propensity model, computes expected value, applies constraints and selects the highest-utility eligible action.

### ML layer
A propensity model estimates `P(response | customer, action, context)`. A later maturity stage should introduce uplift/treatment-effect models to optimize incremental effect rather than correlation alone.

### Data layer
Production data is expected to live in governed Fabric/OneLake datasets or be exposed through approved shortcuts/mirroring patterns. Feature contracts should be versioned independently from the model.

## 3. Decision sequence

```text
Request
  -> validate customer context
  -> load candidate-action catalog
  -> eligibility pre-checks
  -> feature materialization
  -> propensity inference
  -> expected-value calculation
  -> deterministic policy constraints
  -> utility ranking
  -> minimum-utility gate
  -> decision + alternatives + versions
  -> append audit event
```

## 5. Trust boundaries

- No model or agent receives unrestricted credentials.
- Managed identities are preferred over embedded secrets.
- Tool schemas are explicit and least-privilege.
- Agent tool output is treated as data; the LLM cannot silently mutate authoritative fields.
- Policy decisions emit policy and model version identifiers.
- Sensitive attributes should be excluded unless formally approved for the use case.

## 6. Observability

Capture at minimum:

- request / correlation id
- customer segment or privacy-safe cohort
- selected action
- candidate scores
- exclusion reasons
- model version
- feature-contract version
- policy version
- latency
- downstream execution outcome
- realized conversion / margin when observable
- agent tool-call correctness
- groundedness / unsupported-claim rate
- token and inference cost

## 7. Maturity path

M0: heuristic local model and deterministic policies.

M1: supervised propensity model + offline validation.

M2: registered model, monitored inference endpoint and production features.

M3: randomized experimentation and causal/uplift modeling.

M4: constrained optimization across customer, inventory and budget portfolios.

M5: agentic orchestration across pricing, inventory, CRM and campaign tools with human approval for high-impact actions.
